# req-spec.json

구현요건 탭의 요구와 기능 명세. 에이전트가 init 절차에서 쓴다. 근거 AC 와 담당 스토리는 `reqs.json`(`references/reqs.md`).

## 스키마

```json
{
  "excluded": "범위에서 뺀 것: 외부 결제 연동(별도 저장소). 근거 파일:줄은 저장소 루트 기준.",
  "users": [
    {
      "text": "설정 파일 하나로 서버 포트와 제목을 바꿈",
      "source": "README.md:12-18",
      "specs": [
        { "text": "config.json 의 port 를 읽어 바인드", "acs": ["AC-3"], "note": "src/config.js:40-52" },
        { "text": "형식이 틀린 칸은 기본값과 경고", "acs": ["AC-4"], "state": "part", "note": "경고만 있고 기본값 대체 없음(src/config.js:60)" }
      ]
    }
  ],
  "stories": { "A1": ["기본 화면", "목록과 상세 화면, 빈 상태 안내"], "A2": "설정 읽기" }
}
```

| 키 | 형식 | 필수 | 뜻 |
|---|---|---|---|
| `users` | 배열 | 예 | 요구 묶음. 요구 원문 단위 |
| `users[].text` | 문자열 | 예 | 요구 원문(문서나 이슈의 문장을 줄여 씀) |
| `users[].source` | 문자열 | 밀도 | 원문 근거 `파일:줄` |
| `users[].specs` | 배열 | 예 | 기능 명세 |
| `specs[].text` | 문자열 | 예 | 기능 명세 한 줄 |
| `specs[].acs` | 문자열 배열 | 아니오 | 근거 AC id. `reqs.json` 의 `acs[].id` 에 있어야 함 |
| `specs[].state` | `done`, `part`, `doing`, `todo`, `unv`, `excl`, `none` | 아니오 | 따로 판정한 결과. 스토리 판정보다 앞섬 |
| `specs[].note` | 문자열 | `state` 가 있으면 밀도 | 판정 근거(`파일:줄`, 시험 이름) |
| `stories` | `{id: [이름, 내용]}` 또는 `{id: 이름}` | 아니오 | 아래 스토리 표. id 는 `config.json` 의 `stories` 와 맞춤 |
| `excluded` | 문자열 | 아니오 | 범위에서 뺀 것. 판정 규칙 문구 뒤에 붙음 |

- 모르는 키는 무시한다
- `state` 값의 화면 이름: `done` 완료, `part` 일부, `doing` 진행 중, `todo` 미구현, `unv` 미검증, `excl` 대상 제외, `none` 명세 없음

## 판정 순서

| 순서 | 조건 | 결과 |
|---|---|---|
| 1 | 명세에 `state` 있음 | 그 `state` |
| 2 | `acs` 가 있고 대응 스토리가 있음 | 담당 스토리가 모두 완료면 완료, 일부면 일부, 남은 스토리에 진행 중이 있으면 진행 중, 완료가 없으면 미구현 |
| 3 | `acs` 가 있고 대응 스토리가 없음(스토리 없는 프로젝트 포함) | 미검증 |
| 4 | `acs` 가 비고 `state` 없음 | 명세 없음 |

- 묶음 상태: 대상 제외를 뺀 명세로 아래 차례의 첫 줄. 모두 대상 제외면 대상 제외
  1. 모두 완료면 완료
  2. 진행 중이 있으면 진행 중
  3. 완료나 일부가 있으면 일부
  4. 모두 명세 없음이면 명세 없음
  5. 모두 미검증이나 명세 없음이면 미검증
  6. 그 밖 미구현
- 완료율: 완료 / (명세 수 - 대상 제외)
- 판정 규칙 문구는 `config.json` 의 `text.reqRule`. 기본 문구 그대로이고 담당 스토리 칸이 없으면(스토리가 없고 AC 에 담당 스토리도 없음) `state` 판정 문구가 대신 보인다
- 담당 스토리 칸이 없으면(스토리 없는 프로젝트) "구현 여부" 머리글을 꺾지 않는다

## 작성 지침

- 요구는 원문 단위로 묶는다. 출처가 README 의 기능 목록이면 항목 하나가 요구 하나
- 명세마다 AC 를 1개 이상 단다. 스토리가 있으면 그 AC 가 `reqs.json` 에서 담당 스토리 1개 이상을 가리키게 한다
- 스토리가 없는 프로젝트: 명세마다 `state` 와 `note` 를 쓴다. 아래 표로 고른다

  | 확인한 것 | `state` | `note` |
  |---|---|---|
  | 명세를 구현한 코드를 읽어 `파일:줄` 로 확인 | `done` | 코드 `파일:줄`. 이름이 맞는 시험이 있으면 시험 이름을 덧붙임 |
  | 코드에 일부만 있음 | `part` | 있는 부분 `파일:줄` 과 빠진 것 |
  | 시험 이름만 봄(코드를 읽지 않음), 또는 아무것도 확인 못 함 | `unv` | 본 시험 이름이나 "근거 못 찾음" |

  - init 은 시험을 실행하지 않는다. 시험 이름은 보조 근거다. 시험 이름만으로 `done` 을 쓰지 않는다
- `note` 에는 근거 `파일:줄` 이나 시험 이름을 쓴다. 추측을 쓰지 않는다
- `check` 검사: 형식, `state` 값, `acs` 가 `reqs.json` 에 있음. `reqs.json` 이 없는데 `acs` 가 있으면 WARN(미검증으로 판정)
