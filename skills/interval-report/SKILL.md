# interval-report: 장기 수행 중간 보고 (docs/intermission.md)

장기 수행은 사람에게 보이지 않는다. 사용자는 지시를 넣고 나면 지금 어디쯤인지, 언제 끝나는지, 그동안 무슨 일이 있었는지 알 방법이 없다.
이 스킬은 그 공백을 `docs/intermission.md` 파일 하나로 메우고, **계획된 작업이 끝날 때까지 그 파일을 갱신한다.**
읽는 사람이 전체 trajectory 를 한 번에 파악할 수 있어야 한다. 그게 이 파일의 유일한 존재 이유다.

여기서 오작동의 대가는 느린 진행이 아니라 **거짓 보고**다. 시각을 추측하면 elapsed 가 허구가 되고, 자신감 있는 단일 숫자 ETA 를 뱉으면 사용자가 그걸 믿고 계획을 세운다.
그래서 아래의 실측 규칙과 ETA 정직성 규칙은 보고의 매끄러움보다 우선한다. 답변은 한글(기술 토큰·경로·명령은 영문).

**런타임:** 외부 도구·프레임워크 의존이 없다. 필요한 것은 `date` 와 파일 쓰기뿐이라 Claude Code(OMC)·Codex CLI(OMX) 양쪽에서 동일하게 동작한다.

- **시각의 출처는 `date` 하나다.** 두 런타임 모두 컨텍스트에 시:분 시각이 없다. 이건 직접 관측된 사실이고, 매번 셸에서 실측하는 **유일한 근거**다.
- **ultragoal 이 있으면 읽고, 없어도 동작한다**(아래 "ultragoal 관계").
- **자가 트리거는 설치하지 않는다.** 이 스킬은 호출되면 동작한다(아래 "When NOT to use").

## When to use
- 사용자 지시 하나가 여러 단계·긴 시간으로 늘어나, 중간에 사람이 상태를 볼 수 없는 수행.
- 자리를 비운 사용자가 돌아와 그동안의 trajectory 를 한 번에 파악해야 할 때.
- 진행 중 사용자가 알아야 할 일이 생겼는데(가정이 깨짐, 외부 대기, 예상 밖 발견) 지금 당장 물을 만큼은 아닐 때.
- 사용자가 `interval-report`/`중간 보고`/`진행 상황 보고`/`intermission` 이라고 할 때.

## When NOT to use
- **단발 작업.** 한 번에 끝나는 일에 보고 파일을 세우면 파일 관리가 작업보다 비싸다.
- **상태의 원본 저장소로.** 이 스킬은 렌더러지 원장이 아니다. 진행 상태의 원본이 필요하면 `ultragoal` 이다.
- **컨텍스트 임계 감지·자동 발화.** statusLine·hook 으로 스스로 발화하려 들지 마라. **그 영역은 `smart-compact` 소유다.** 트리거 메커니즘을 복제하지도, 설치하지도 않는다. interval-report 는 호출되면 동작하고, 갱신 시점은 아래 "3. 갱신 리듬" 이 정한다.
- **compaction 직전 준비.** 그건 `ready-compact` 다. 이름이 비슷해 헷갈리지만 하는 일이 다르다.

| | interval-report | ready-compact |
|---|---|---|
| 계기 | **연속**(작업이 끝날 때까지 갱신) | 이벤트 1회성(compaction 직전) |
| 독자 | **사람** | 다음 세션의 에이전트 |
| 산출물 | `docs/intermission.md`(자급식 보고서) | 붙여넣기용 resume 프롬프트 |
| 담는 것 | trajectory 전체(시작·경과·잔여·이벤트) | 휘발성 맥락(다음 한 수) |
| 시간 | **핵심**(실측·영속·ETA) | 범위 밖 |

둘은 같은 세션에서 공존한다. 경쟁하지 않는다. 보고서가 있다고 resume 프롬프트를 생략하지 말고, 그 반대도 마찬가지다.

## 측정 범위 (여기가 틀리면 나머지 숫자가 전부 틀린다)

측정 대상은 세션 전체가 아니라 **마지막 사용자 지시로 시작된 현재 수행분**이다.

> **시작 시각 = 마지막으로 사용자가 대화·지시한 시점.**

- 세션은 며칠을 살아 있을 수 있고 그중 대부분은 사용자가 자리에 없던 시간이다. 세션 시작을 기준으로 잡으면 elapsed 는 "이 지시가 얼마나 걸리고 있나" 가 아니라 "이 터미널이 얼마나 오래 열려 있나" 를 재게 된다. 후자는 아무도 궁금해하지 않는다.
- 사용자가 **새 지시**를 넣으면 그것이 새 수행분이다. 시작 시각을 새로 찍고 보고서를 새로 연다.
- 사용자의 개입이 지시가 아니라 **승인·답변**(예: "응", "그렇게 해", "1번으로")이면 수행분은 이어진다. 시작 시각을 옮기지 마라.
- 애매하면 **옮기지 않는 쪽**을 택한다. 두 실수의 대가가 대칭이 아니다. 옮기는 실수는 elapsed 를 낙관 쪽으로 붕괴시키고, 안 옮기는 실수는 비관 쪽으로 어긋난다. 보고서에서는 낙관 편향이 더 나쁘다.

## 시간 메커닉

### 실측
```bash
date +%s                    # epoch 초. 산술은 이 값으로만.
date '+%Y-%m-%d %H:%M %Z'   # 사람이 읽는 표기. 보고서에 그대로 싣는다.
```

시각을 추측하거나 대화 내용에서 역산하지 마라. 두 런타임 모두 컨텍스트에 시:분 시각이 없다.
이 문장이 `date` 를 부르는 근거의 전부다. 다른 근거를 덧붙이지 마라.

### READ-BACK 불변 규칙 (이 스킬의 핵심 안전장치)

> **파일에 이미 시작 시각이 있으면 절대 덮어쓰지 않는다.**

갱신할 때는 언제나 파일을 먼저 읽는다. 계산은 그다음이다.

```bash
F=docs/intermission.md
if [ -f "$F" ] && grep -q '^started_epoch:' "$F"; then
  START=$(grep -m1 '^started_epoch:' "$F" | tr -cd '0-9')   # 파일이 정본
else
  START=$(date +%s)                                          # 최초 1회만
fi
NOW=$(date +%s)
ELAPSED=$(( NOW - START ))
printf 'start=%s elapsed=%dh %02dm\n' "$START" $(( ELAPSED / 3600 )) $(( ELAPSED % 3600 / 60 ))
```

- **왜 영속이 필수인가:** compaction·resume 후에는 모델이 시작 시각을 기억하지 못한다. 그때 `now` 로 재스탬프하면 elapsed 가 0 으로 붕괴한다. 붕괴는 조용하고, 하필 **긴 작업일수록 잘 일어난다**(길수록 compaction 을 겪으니까). 즉 리포트가 가장 필요한 순간에 리포트가 가장 낙관적으로 거짓말한다. 이 규칙은 편의보다 우선한다.
- **정수 산술만 쓴다.** `date -d @...`(GNU)와 `date -v`(BSD)는 문법이 갈린다. `date +%s` 로 epoch 만 얻고 뺄셈은 셸에 맡기면 분기가 사라진다.
- **사람이 읽는 표기도 같이 영속한다.** epoch 만 두면 파일을 연 사람이 값을 검증할 수 없다.

## ETA 정직성

ETA 는 **실측량에서만** 유도한다: 경과 시간, 완료 수, 진행중 수, 대기 수. 이 넷 말고 다른 입력을 지어내지 마라.

**규칙 1. 단일 숫자 금지. 범위 + 확신 라벨.**
- 나쁨: `예상 종료: 17:30`
- 좋음: `예상 잔여: 40m ~ 2h (확신: 낮음)` / `예상 종료: 17:00 ~ 18:20 KST`
- 확신 라벨은 3단이면 충분하다: 높음 / 보통 / 낮음. 소수점 확신도가 필요하면 그건 `curation` 의 형식이지 여기가 아니다.

**규칙 2. 가정을 인라인에 적는다.**
ETA 바로 옆이나 바로 아래에 무엇을 가정했는지 쓴다. 별도 문서로 미루지 마라. 읽는 사람이 ETA 를 보는 **그 자리에서** 가정을 봐야 정정할 수 있다.

> 예상 잔여: 40m ~ 2h (확신: 낮음)
> 가정: 남은 3건이 끝난 2건과 비슷한 크기다(확인된 바 없음). 5번이 사용자 승인 대기라 상한이 열려 있다.

**규칙 3. 90% 천장을 의식한다.**
카운트가 9/10 을 가리킬 때가 **남은 노력이 가장 클 수 있는 지점**이다. 마지막 항목은 대개 통합·검증·사용자 확인이고, 그것들은 앞의 9개와 크기가 다르다.
선형 외삽(경과 ÷ 완료 × 대기)은 초반에 그럭저럭 맞고 **꼬리에서 무너진다.** 꼬리에서 성립하는 척하지 마라.
- 카운트가 올라갈수록 범위의 **상한을 좁히지 마라.** 좁히고 싶은 충동이 정확히 그 편향이다.
- 남은 항목의 성격이 앞의 항목과 다르면(검증·리뷰·사용자 결정 대기) 그 사실을 가정에 적고 확신을 낮춘다.
- 진행률 퍼센트 하나로 요약하지 마라. 작업 표의 카운트가 이미 그 정보를 편향 없이 담고 있다.

**규칙 4. 자기모순 금지.**
"정직한 ETA" 를 표방하면서 자신감 있는 단일 숫자를 뱉으면 자기모순이다. 그건 ETA 를 아예 안 내는 것보다 **나쁘다.** 사용자가 정직성 표방을 믿고 그 숫자를 더 신뢰하기 때문이다.
범위를 못 내겠으면 **"모른다" 고 적어라.** 그건 허용된 답이다. 근거 없는 숫자를 채워 넣는 것만 금지다.

## ultragoal 관계 (렌더러지 원장이 아니다)

`ultragoal` 은 목표 목록·상태·타임스탬프를 append-only 원장으로 **양 런타임에 이미 영속화**한다. 이 스킬은 그것을 복제하지 않는다.

- **있으면 읽어서 렌더한다.** 작업 표의 순서·작업·상태를 원장에서 채우고, 보고서에 원장 경로를 출처로 적는다.
  - Claude(OMC): `.omc/ultragoal/`
  - Codex(OMX): `.omx/ultragoal/`
- **없어도 동작한다.** ultragoal 은 opt-in 이라 대부분의 세션에 없다. 없으면 현재 지시의 작업 목록에서 표를 직접 만든다. **ultragoal 을 요구하지도, 대신 켜지도 마라.**
- **상태를 복제하지 않는다.** 보고서는 원장의 파생물이다. 둘이 어긋나면 원장이 맞다. 보고서를 고쳐 원장을 반영하지, 원장을 보고서에 맞추지 않는다.
- **왜 그 위에 얹는가:** ultragoal 에는 시간·ETA 개념이 없고 산출물이 기계 포맷이다. 이 스킬이 더하는 것은 딱 두 가지다. 얇은 시간 레이어(실측·영속·경과·ETA), 그리고 사람용 렌더러. 그 둘을 넘어가면 ultragoal 을 다시 구현하는 것이다.

## 워크플로

### 0. READ-BACK (추정 금지)
언제나 여기서 시작한다. 파일이 있는지, 시작 시각이 무엇인지 **읽어서** 확인한다. 기억에 의존하지 마라.
위 "READ-BACK 불변 규칙" 의 블록을 그대로 돌려 `START`·`ELAPSED` 를 얻는다. 여기서 읽은 `started_epoch` 는 4단계 검증의 기준값이다.

파일이 없으면 최초 실행이다. 1단계로 간다. 있으면 **갱신**이다. 3단계로 간다.

### 1. 자리 잡기 (docs/ + .gitignore, 최초 1회)
산출물은 타깃 repo 의 `docs/intermission.md` 다. `docs/` 가 없으면 만든다.

이건 **세션 로컬 작업물**이지 그 프로젝트의 문서가 아니다. 커밋되면 우리 세션의 진행 상황이 남의 repo 히스토리에 영구히 남는다. 그래서 `.gitignore` 에 기본 항목을 추가한다.

```
# interval-report: session-local progress report (not project documentation)
docs/intermission.md
```

- **`.gitignore` 는 그 프로젝트의 파일이지 우리가 만든 게 아니다.** 그러므로 **사용자에게 알리고 진행한다.** 무엇을 왜 추가하는지 한 줄로 말하면 된다. 승인을 기다리며 멈추라는 게 아니라, 사용자가 모르는 채로 남의 repo 가 바뀌는 일을 막으라는 것이다.
- **멱등하게.** 이미 그 항목이 있으면 추가하지 않는다. 이미 무시되고 있어도(상위 규칙, `docs/` 통째 무시 등) 추가하지 않는다. 확인은 이걸로 한다:
  ```bash
  git check-ignore -q docs/intermission.md && echo "이미 무시됨: 추가 불필요"
  ```
- git repo 가 아니면(`git rev-parse --git-dir` 실패) 이 단계를 통째로 건너뛴다. 에러가 아니다.
- 사용자가 보고서를 커밋 대상으로 원한다고 명시하면 그건 사용자의 repo 다. 추가하지 말고 그대로 둔다.

### 2. 보고서 렌더
필수 항목 8개는 **전부** 있어야 한다: 시작 시간 / 현재 상태 / elapsed / 예상 잔여 / 예상 종료 / 진행·잔여 작업 표 / 발생 이벤트 / 인지 중인 constraints.

**작업 표는 하나다.** 완료분과 잔여분을 따로 두지 마라. 하나의 표에 순서대로 놓아야 trajectory 가 한눈에 들어온다. 상태 값은 `완료`·`진행중`·`대기` 3종뿐이다.

```markdown
---
started_epoch: 1784181572
started_human: "2026-07-16 14:59 KST"
updated_human: "2026-07-16 16:20 KST"
---

# 중간 보고: DB 마이그레이션 롤아웃

| 항목 | 값 |
|---|---|
| 시작 | 2026-07-16 14:59 KST |
| 현재 상태 | 3번(스테이징 검증) 진행 중. 4번부터 대기. |
| elapsed | 1h 21m |
| 예상 잔여 | 40m ~ 2h (확신: 낮음) |
| 예상 종료 | 17:00 ~ 18:20 KST |

**ETA 가정:** 남은 3건이 끝난 2건과 비슷한 크기다(확인된 바 없음). 5번이 사용자 승인 대기라 상한이 열려 있다.

## 작업

| # | 작업 | 상태 |
|---|---|---|
| 1 | 스키마 diff 추출 | 완료 |
| 2 | 마이그레이션 스크립트 작성 | 완료 |
| 3 | 스테이징 검증 | 진행중 |
| 4 | 롤백 절차 문서화 | 대기 |
| 5 | 운영 반영 | 대기 |

## 발생 이벤트
- 15:34 스테이징 시드가 3개월 낡아 일부 검증을 건너뜀. 사용자 판단이 필요할 수 있음.
- 16:02 `npm i` 가 프록시 뒤에서 2회 실패. 재시도로 통과. 조치 불필요.

## 인지 중인 constraints
- 운영 반영은 사용자 승인 후에만(전역 규칙).
- 스테이징 DB 는 18:00 에 야간 배치가 잡아간다. 3번을 그 전에 끝내야 한다.
- 롤백 절차는 아직 검증되지 않았다. 5번의 전제 조건이다.
```

- **발생 이벤트**는 사용자가 알아야 할 것만 적는다. 로그가 아니다. 기준은 "이걸 몰랐다면 사용자가 다르게 판단했을까" 다. 아니면 빼라. 다만 **가정이 깨진 사건은 반드시 남긴다.**
- **constraints** 는 지금 인지하고 있는 제약이다. 환경·순서 의존·승인 게이트·외부 대기. 사용자가 풀어줄 수 있는 것이 여기 있으면 그게 이 절의 값어치다.
- 항목에 쓸 내용이 없으면 항목을 **지우지 말고** "없음" 이라고 적는다. 없는 항목과 빈 항목은 다르다.

### 3. 갱신 리듬
갱신은 **계획된 작업이 끝날 때까지** 이어진다. 시점은 사건이 정한다:

- 작업 표의 항목 상태가 바뀌었을 때(완료·진행중 전환).
- 사용자가 알아야 할 이벤트가 생겼을 때.
- constraints 가 바뀌었을 때(제약이 생기거나 풀렸을 때).
- ETA 의 가정이 깨졌을 때. **이때가 가장 중요하다.** 가정이 깨졌는데 ETA 를 그대로 두면 그 순간부터 보고서는 거짓이다.
- 사용자가 물었을 때.

매 갱신마다 0단계 READ-BACK 을 먼저 한다. `updated_human` 을 새로 찍고 `started_epoch` 는 손대지 않는다.
갱신할 게 없으면 갱신하지 않는다. 같은 내용으로 타임스탬프만 바꾸는 것은 신호가 아니라 잡음이다.

### 4. 검증 (보고 의무)
**보고서를 썼다는 사실로 성공을 선언하지 마라.** 파일은 언제나 써진다. 붕괴한 시작 시각도, 자신감 있는 단일 숫자도 똑같이 잘 써진다.
판정은 **갱신할 때마다** 아래를 실제로 돌려서 한다.

```bash
F=docs/intermission.md
grep -m1 '^started_epoch:' "$F"        # 0단계에서 읽은 값과 동일해야 한다
grep -m1 '^started_human:' "$F"
git check-ignore -q "$F" 2>/dev/null && echo "gitignore: ok" || echo "gitignore: 미적용 (git repo 가 아니면 정상, 아니면 1단계 확인)"
```

체크리스트. 하나라도 아니오면 고치고 다시 본다.
- `started_epoch` 가 0단계에서 읽은 값과 **같은가.** 다르면 재스탬프 사고이고 elapsed 는 거짓이다. 즉시 원래 값으로 되돌린다.
- elapsed 가 **직전 보고보다 커졌는가.** 줄었으면 같은 사고다.
- 필수 항목 8개가 **전부 있는가.** "없음" 도 값이다. 항목 자체를 지우지 않는다.
- 작업 표가 **하나인가.** 상태 값이 완료·진행중·대기 3종뿐인가.
- ETA 가 **범위 + 확신 라벨**인가. 단일 시각 하나면 규칙 위반이다.
- ETA 옆에 **가정이 적혀 있는가.** 가정이 지금도 유효한가.
- 표의 상태가 실제 진행과 맞는가. **갱신하지 않은 보고서는 오래된 보고서가 아니라 틀린 보고서다.**

사용자에게는 파일 경로와 함께 **지금 값**을 한 줄로 준다. 파일을 열게 하지 마라.

```
docs/intermission.md 갱신: elapsed 1h 21m, 2/5 완료, 예상 잔여 40m ~ 2h (확신: 낮음)
```

## 함정
- **now 로 재스탬프하는 것.** 이 스킬에서 데이터가 거짓이 되는 유일하고 실재하는 경로다. 파일에 시작 시각이 있으면 그게 정본이다.
- **세션 시작을 시작 시각으로 잡는 것.** 측정 대상은 마지막 사용자 지시로 시작된 수행분이다.
- **승인 한마디를 새 지시로 오인해 시작 시각을 옮기는 것.** 애매하면 옮기지 않는다.
- **자신감 있는 단일 숫자.** "정직한 ETA" 를 표방하면서 이걸 하면 자기모순이고, 침묵보다 나쁘다.
- **꼬리에서 선형 외삽을 믿는 것.** 9/10 이 남은 노력이 가장 큰 지점일 수 있다.
- **표를 둘로 쪼개는 것.** 완료 표와 잔여 표를 나누면 trajectory 가 끊긴다. 표는 하나다.
- **이벤트 절을 로그로 만드는 것.** 전부 적으면 아무것도 안 적은 것과 같다. 기준은 "사용자의 판단이 달라졌을까" 다.
- **파일만 쓰고 끝내는 것.** 파일은 언제나 써진다. 검증은 4단계 체크리스트다.
- **`.gitignore` 를 정리하려 드는 것.** 여기서 하는 일은 한 줄 멱등 추가지 정리가 아니다(정리는 `refresh-git-ignore` 소관이고 이 스킬이 부를 일이 아니다).
- **남의 repo 를 조용히 건드리는 것.** `.gitignore` 변경은 알리고 진행한다.
- **`date` 의 계산 옵션에 의존하는 것.** GNU 와 BSD 가 갈린다. epoch 뺄셈만 쓴다.
- **ultragoal 상태를 보고서에 복제하는 것.** 어긋나면 원장이 맞다.
- **자가 트리거를 설치하는 것.** `smart-compact` 영역이다.
- **보고서를 resume 프롬프트로 쓰는 것.** 그건 `ready-compact` 다. 독자가 다르다(사람 대 에이전트).

## 원칙
- 시각은 `date` 로 실측한다. 추측·역산 금지.
- 시작 시각은 파일이 정본이다. READ-BACK 이 먼저, 계산은 그다음.
- 측정 단위는 세션이 아니라 마지막 사용자 지시로 시작된 수행분이다.
- ETA 는 실측량에서만 유도하고, 범위 + 확신 라벨로 내고, 가정을 곁에 적는다.
- 모르면 모른다고 적는다. 그게 허용된 답이고 자신 있는 오답보다 낫다.
- 표는 하나다. 전체 trajectory 가 한눈에 들어와야 한다.
- 이 스킬은 시간 레이어와 렌더러다. 원장도, 트리거도, resume 프롬프트도 아니다.
- 산출물은 세션 로컬이다. 남의 repo 에 남기지 않는다.
- 계획된 작업이 끝날 때까지 갱신한다. 끝나면 마지막 갱신으로 닫는다.

ARGUMENTS: [--path <파일>] [--close] [지시 요약] (없으면 `docs/intermission.md` 에 현재 수행분을 렌더하고 계획된 작업이 끝날 때까지 갱신)
- `--path <파일>`: 산출 경로를 바꾼다. `.gitignore` 게이트는 그 경로에 그대로 적용한다.
- `--close`: 마지막 갱신을 하고 보고서를 닫는다. 전 항목을 종료 상태로 맞추고, elapsed 를 확정하고, 예상 잔여·예상 종료를 실제 값으로 대체한다.
- 인자 없이 파일이 이미 있으면 그건 **갱신**이다. 새로 만들지 마라. 언제나 READ-BACK 이 먼저다.
